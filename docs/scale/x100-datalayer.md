# OmniRoute x100 data-layer capacity analysis

Research date: 2026-07-29. Target build: OmniRoute v3.8.48. This is a read-only
production assessment. No production database, container, or remote server was modified.

## Executive verdict

**SQLite survives the corrected x100 peak of 20.8 client requests/second on this box from a
write-throughput perspective. The data layer as currently configured does not yet survive x100
operationally.** A copied-database microbenchmark sustained 3,926 logical requests/second with the
observed SQL write shape plus a synchronous artifact write: 189 times the target. PostgreSQL is not
needed to reach this traffic level. The actual blockers are data lifetime, synchronous body-artifact
I/O, cardinality-unbounded exports, and a billing durability/observability gap at the SQLite boundary
([E2](#e2-copied-database-write-benchmark),
[src/lib/db/core.ts:1119](../../src/lib/db/core.ts#L1119)).

The recommended x100 design is therefore **SQLite for control-plane and bounded operational data,
with durable billing writes and aggressively bounded or externalized request telemetry**. If a later
requirement calls for long raw-history retention or analytical scans, move high-volume telemetry to
an append queue plus object storage/ClickHouse-class analytics store first; do not rewrite all 119
SQLite migrations merely to handle 20.8 requests/second. Multi-instance topology is deliberately out
of scope.

## Scope and load model

This report uses the corrected client-facing targets supplied for this assessment:

| Load | Client requests/day | Sustained peak |
| --- | ---: | ---: |
| Current | 4,427 | not re-derived |
| x10 | 44,270 | 2.1 requests/second |
| x100 | 442,700 | 20.8 requests/second |

The supplied current total, including other sources, is about 11,800 requests/day. Projections below
apply the observed production write ratios to 44,270 and 442,700 requests/day. They do not include
OAuth subscription economics or multi-instance behavior.

## 1. Write path and throughput ceiling

### Writes generated by a request

A successful chat attempt normally generates the following data-layer work:

1. `call_logs`: `persistAttemptLogs()` passes bounded request and response bodies to `saveCallLog()`
   ([open-sse/handlers/chatCore/attemptLogging.ts:165](../../open-sse/handlers/chatCore/attemptLogging.ts#L165)).
   Unless `noLog` is active, `saveCallLog()` serializes an artifact, synchronously writes a temporary
   file and renames it, then inserts the summary row
   ([src/lib/usage/callLogs.ts:609](../../src/lib/usage/callLogs.ts#L609),
   [src/lib/usage/callLogArtifacts.ts:197](../../src/lib/usage/callLogArtifacts.ts#L197),
   [src/lib/usage/callLogs.ts:643](../../src/lib/usage/callLogs.ts#L643)). This is **one filesystem
   write/rename and one DB row** per logged attempt, not one per end-user request in every routing
   case.
2. `usage_history`: the usage recorder performs a deduplication read and transactional insert
   ([src/lib/usage/usageHistory.ts:607](../../src/lib/usage/usageHistory.ts#L607),
   [src/lib/usage/usageHistory.ts:661](../../src/lib/usage/usageHistory.ts#L661)). The non-streaming
   and streaming callers do not await or inspect its Promise
   ([open-sse/handlers/chatCore/nonStreamingUsageStats.ts:42](../../open-sse/handlers/chatCore/nonStreamingUsageStats.ts#L42),
   [open-sse/handlers/chatCore/streamingUsageStats.ts:33](../../open-sse/handlers/chatCore/streamingUsageStats.ts#L33)).
3. `proxy_logs`: each executor attempt schedules `safeLogEvents()` fire-and-forget
   ([src/sse/handlers/chat.ts:1418](../../src/sse/handlers/chat.ts#L1418)); it calls `logProxyEvent()`
   once and that performs the insert
   ([src/sse/handlers/chatHelpers.ts:785](../../src/sse/handlers/chatHelpers.ts#L785),
   [src/lib/proxyLogger.ts:142](../../src/lib/proxyLogger.ts#L142)). Retries and combo attempts explain
   why this table grows faster than call rows.
4. `domain_cost_history`: only a request with an API key and positive estimated cost is enqueued
   ([open-sse/handlers/chatCore.ts:4113](../../open-sse/handlers/chatCore.ts#L4113)). The buffer flushes
   after 60 seconds or 1,000 entries, and persists a batch in one transaction
   ([src/lib/spend/batchWriter.ts:22](../../src/lib/spend/batchWriter.ts#L22),
   [src/lib/spend/batchWriter.ts:72](../../src/lib/spend/batchWriter.ts#L72),
   [src/lib/db/domainState.ts:383](../../src/lib/db/domainState.ts#L383)). This is an optional fourth
   row, but not a fourth immediate transaction.

The accurate hot-path description is therefore **three immediate row writes plus one artifact per
successful logged attempt, with an optional buffered cost row**. It is not a fixed number per client
request: the copied DB's last complete 24-hour window contained 13,016 `call_logs`, 13,016
`usage_history`, 37,983 `proxy_logs`, and 9,389 cost rows, or 1.00, 1.00, 2.918, and 0.721 rows per
call row respectively ([E1](#e1-read-only-database-observations)). At x100 peak, a one-attempt request
would be 62.4 immediate SQL row writes/second, or up to 83.2 including cost; the observed proxy
amplification implies approximately 97 immediate rows/second plus buffered cost at the same 20.8
request/second arrival rate.

### Copied-database benchmark

The live DB was never opened for a benchmark. I used SQLite's online backup command with a five
second busy timeout to create `/tmp/omniroute-x100.QpUrly/storage-copy.sqlite`; its size was
177,070,080 bytes and `PRAGMA quick_check` returned `ok` ([E2](#e2-copied-database-write-benchmark)).
All test writes targeted another copy under `/tmp`.

The `node:sqlite` benchmark used the production WAL and `synchronous=NORMAL` settings and the actual
table/index layout. Each of 10,000 synthetic logical requests inserted one `call_logs`, one
`usage_history`, one `proxy_logs`, and a representative optional cost row pattern, plus wrote and
renamed a 7,843-byte artifact. It sustained **3,926.2 logical requests/second end-to-end**; the SQL
portion alone sustained 4,803.5/second. The 20.8 request/second target consumes 0.53% of that measured
ceiling. A no-artifact comparison produced 5,345/second with `NORMAL` and 5,431/second with `FULL`,
so `FULL` had no measurable penalty in this warm-cache run ([E2](#e2-copied-database-write-benchmark)).

This is a single-process microbenchmark, not an SLA: it has warm caches, synthetic payloads, and no
concurrent UI scan or cleanup. The driver is synchronous, and a contended call may park the Node
event loop for the configured two-second busy timeout
([src/lib/db/core.ts:1121](../../src/lib/db/core.ts#L1121)). It nevertheless shows plainly that raw
SQLite write throughput is not the x100 limit on this host.

## 2. Growth and retention

### Unretained growth projection

`dbstat` on the safe copy, including each table's indexes, measured 740.0 bytes per `call_logs` row,
550.2 per `usage_history`, 360.4 per `proxy_logs`, and 177.1 per cost row
([E1](#e1-read-only-database-observations)). Applying the observed 24-hour row ratios gives:

| Load | Table | Rows/day | Rows/week | Rows/30 days |
| --- | --- | ---: | ---: | ---: |
| x10 | `call_logs` | 44,270 | 309,890 | 1,328,100 |
| x10 | `usage_history` | 44,270 | 309,890 | 1,328,100 |
| x10 | `proxy_logs` | 129,188 | 904,314 | 3,875,632 |
| x10 | `domain_cost_history` | 31,934 | 223,537 | 958,016 |
| x100 | `call_logs` | 442,700 | 3,098,900 | 13,281,000 |
| x100 | `usage_history` | 442,700 | 3,098,900 | 13,281,000 |
| x100 | `proxy_logs` | 1,291,877 | 9,043,141 | 38,756,317 |
| x100 | `domain_cost_history` | 319,339 | 2,235,370 | 9,580,156 |

These four tables and their current indexes add approximately **0.109 GB/day, 0.765 GB/week, and
3.28 GB/30 days at x10**, or **1.093 GB/day, 7.65 GB/week, and 32.8 GB/30 days at x100**, before
page reuse and WAL transients. The supplied whole-DB historical density of 3.7 KB/request is a more
conservative envelope: 0.164/1.15/4.91 GB per day/week/30 days at x10, and
1.638/11.47/49.14 GB at x100. Both calculations are reproducible from [E1](#e1-read-only-database-observations)
and the load table above.

Current artifacts average 8,904.5 bytes across 10,002 files
([E3](#e3-live-filesystem-read-only-observations)). Without a count cap, that rate is
**0.394 GB/day, 2.76 GB/week, 11.83 GB/30 days at x10** and **3.94 GB/day, 27.59 GB/week,
118.26 GB/30 days at x100**. The hard 512 KiB per-artifact bound is not a retention policy; its
uncapped worst case would be 23.21 GB/day at x10 and 232.10 GB/day at x100
([src/lib/usage/callLogArtifacts.ts:11](../../src/lib/usage/callLogArtifacts.ts#L11)).

### What actually runs

With the environment variables unset, code defaults are seven days for call and app-log age,
10,000 artifact files, 100,000 `call_logs` rows, 100,000 proxy rows, 50 MiB per application log,
and 20 rotated application logs
([src/lib/logEnv.ts:4](../../src/lib/logEnv.ts#L4),
[src/lib/logEnv.ts:74](../../src/lib/logEnv.ts#L74),
[src/lib/logEnv.ts:106](../../src/lib/logEnv.ts#L106)). The documented 10,000 value is the
**artifact-file cap**, not the table-row cap. Therefore 46,359 `call_logs` rows are expected and do
not show that row retention failed.

`saveCallLog()` schedules `rotateCallLogs()` at most once per minute. That pass deletes call rows by
the seven-day environment default, trims the table to 100,000, caps artifacts at 10,000, and removes
orphans ([src/lib/usage/callLogs.ts:682](../../src/lib/usage/callLogs.ts#L682),
[src/lib/usage/callLogs.ts:688](../../src/lib/usage/callLogs.ts#L688)). The current copy has exactly a
seven-day call span and the filesystem has 10,002 artifacts, confirming this path is active within
its asynchronous race margin ([E1](#e1-read-only-database-observations),
[E3](#e3-live-filesystem-read-only-observations)). At x10 the artifact cap retains only 5.42 average
hours, or 79 minutes at peak; at x100 it retains 32.5 average minutes, or 8.0 peak minutes. The
100,000-row call cap retains 54.2 average hours at x10 and 5.42 hours at x100 (13.2 hours and 80.1
minutes at peak respectively). Retention is bounded, but its diagnostic value collapses at scale.

A separate compliance cleanup runs on every process startup
([src/instrumentation-node.ts:313](../../src/instrumentation-node.ts#L313)). When no explicit env
override exists it honors dashboard values, currently 90 days for call logs and 365 for usage, then
applies the same 100,000 call/proxy caps
([src/lib/compliance/index.ts:489](../../src/lib/compliance/index.ts#L489),
[src/lib/compliance/index.ts:523](../../src/lib/compliance/index.ts#L523),
[E1](#e1-read-only-database-observations)). Runtime call rotation still uses the seven-day default,
so the effective call policy is seven days or 100,000 rows, whichever comes first.

The broader six-hour `runAutoCleanup()` scheduler is **not wired into the production instrumentation
entry point**. Its only start call is in `src/server-init.ts`
([src/server-init.ts:118](../../src/server-init.ts#L118)); the production instrumentation explicitly
describes that file as unused ([src/instrumentation-node.ts:278](../../src/instrumentation-node.ts#L278)).
The running container has the compliance startup log but no “Background cleanup scheduler started”
or `[Cleanup]` line ([E4](#e4-running-process-and-log-observations)). Consequences:

- `usage_history` is age-cleaned only at startup, currently to 365 days. The safer roll-up-before-delete
  logic exists in the unwired scheduler
  ([src/lib/db/cleanup.ts:83](../../src/lib/db/cleanup.ts#L83)); startup cleanup deletes raw usage
  directly ([src/lib/compliance/index.ts:523](../../src/lib/compliance/index.ts#L523)).
- `proxy_logs` is capped to 100,000 only at startup, not continuously. At x100's observed ratio it
  reaches 100,000 in 1.86 average hours, then grows until the next restart. The unwired scheduler
  would delete it by call retention every six hours
  ([src/lib/db/cleanup.ts:475](../../src/lib/db/cleanup.ts#L475),
  [src/lib/db/cleanup.ts:506](../../src/lib/db/cleanup.ts#L506)).
- `domain_cost_history` has no scheduled cleanup at all. A deletion function exists but has no call
  site ([src/lib/db/domainState.ts:455](../../src/lib/db/domainState.ts#L455)); the copied table spans
  2026-04-16 through 2026-07-29 ([E1](#e1-read-only-database-observations)).

### Application and database-backup logs

Application rotation checks every 60 seconds and renames `app.log` at 50 MiB
([src/lib/logRotation.ts:68](../../src/lib/logRotation.ts#L68),
[src/lib/logRotation.ts:165](../../src/lib/logRotation.ts#L165)). At observation time the current
file was 50,347,345 bytes, only 48.0 MiB, so the reported “49 MB” does **not** by itself prove a
current missed threshold. Current rotation is therefore **unverified/inconclusive**, not confirmed
broken. There is, however, evidence of a historical reopen defect: the file named
`app.2026-07-27_155711.log` reached 72,369,769 bytes and continued to receive writes until
2026-07-28 17:40 MSK. A rename does not reopen Pino's already-open destination; the logger creates
the transport once ([src/shared/utils/logger.ts:87](../../src/shared/utils/logger.ts#L87)), while
the rotation code only renames the pathname. The current process has three descriptors to the
current `app.log`, so the next threshold crossing should be explicitly observed before calling the
present build fixed ([E3](#e3-live-filesystem-read-only-observations),
[E4](#e4-running-process-and-log-observations)). Use a transport-aware rotating destination or
explicit close/reopen, then test the inode transition.

From the current file's birth time and size, it grew about 30.8 MB/day at the supplied current total
of 11,800 requests/day, or about 2.61 KB/request. If bytes/request remains constant, the corrected
targets imply approximately **116 MB/day at x10 and 1.16 GB/day at x100**. Correct seven-day
rotation bounds that to about 0.81 GB and 8.1 GB respectively; it does not save write I/O. Disabling
duplicated/nonessential log lines is the only way to reduce that I/O. This projection is explicitly
an extrapolation from [E3](#e3-live-filesystem-read-only-observations), not a production benchmark.

Managed backups live in `data/db_backups`, but age cleanup defaults to zero days (disabled); count
cleanup and age cleanup run after backup creation
([src/lib/db/backup.ts:22](../../src/lib/db/backup.ts#L22),
[src/lib/db/backup.ts:92](../../src/lib/db/backup.ts#L92),
[src/lib/db/backup.ts:163](../../src/lib/db/backup.ts#L163)). The three managed files currently use
228,995,072 bytes. Separately, 12 top-level `storage.sqlite.bak-*` primary files use **968,773,632
bytes**; the April-June subset is nine files and **535,863,296 bytes**. This supersedes the earlier
677 MB estimate. A `/proc` descriptor scan of both running OmniRoute processes found only the live
database, WAL/SHM, and application log—no backup file is open ([E4](#e4-running-process-and-log-observations)).
After owner review of recovery value, archiving or deleting these top-level backups immediately
reclaims 0.969 GB and causes no recurring request I/O saving.

## 3. Pipeline capture

The contradiction is settled: **the runtime pipeline is OFF**. The copied DB contains legacy
`databaseSettings.callLogPipelineEnabled='true'` and authoritative
`settings.call_log_pipeline_enabled='0'` ([E1](#e1-read-only-database-observations)). `chatCore.ts`
reads only `settings.call_log_pipeline_enabled`
([open-sse/handlers/chatCore.ts:782](../../open-sse/handlers/chatCore.ts#L782)); the settings merge
maps that snake-case value into the dashboard object and UI writes update it
([src/lib/db/databaseSettings.ts:143](../../src/lib/db/databaseSettings.ts#L143),
[src/lib/db/databaseSettings.ts:295](../../src/lib/db/databaseSettings.ts#L295)). The camel-case
legacy row does not enable runtime capture.

Pipeline OFF does **not** mean body capture is off. It makes only `pipelinePayloads` null; request and
response bodies are still passed to the call logger
([open-sse/handlers/chatCore/attemptLogging.ts:141](../../open-sse/handlers/chatCore/attemptLogging.ts#L141),
[open-sse/handlers/chatCore/attemptLogging.ts:176](../../open-sse/handlers/chatCore/attemptLogging.ts#L176)).
The copied database confirms 46,332 request bodies, 39,523 response bodies, zero pipeline rows, and
86,425,469 artifact bytes. None of the 10,002 current artifact files contains a `pipeline` field
([E1](#e1-read-only-database-observations), [E3](#e3-live-filesystem-read-only-observations)).
Large request/response objects are summarized above 8 KiB before cloning, with deeper string/array/
depth bounds ([open-sse/handlers/chatCore/logTruncation.ts:61](../../open-sse/handlers/chatCore/logTruncation.ts#L61)),
but ordinary bodies are retained.

There is no production ON sample, so CPU and byte deltas cannot be claimed as measured production
facts. A representative median 1,142-byte artifact was synthetically serialized with the normal
non-stream pipeline fields. It grew to 1,882 bytes (1.65 times); serialization rose from 4.94 to
7.41 microseconds (1.50 times), and temporary-write/rename time from 30.15 to 33.30 microseconds
(1.10 times) ([E5](#e5-synthetic-pipeline-cost-sample)). Stream chunks are enabled by default and the
pipeline cap defaults to 512 KiB, so a real ON workload can be materially larger
([src/lib/logEnv.ts:118](../../src/lib/logEnv.ts#L118)). Treat 1.65 times as a representative estimate,
not a bound.

At the current artifact-size distribution, OFF but body capture enabled costs the 0.394/3.94 GB per
day projected at x10/x100 before the 10,000-file cap. Applying the synthetic 1.65 multiplier gives
about **0.650 GB/day at x10 and 6.50 GB/day at x100** (19.5 and 195 GB/30 days uncapped). The absolute
512 KiB bound remains 23.21/232.10 GB/day. Keeping the pipeline OFF therefore avoids roughly 39% of
the synthetic ON bytes and one-third of its serialization CPU, but it does not remove the synchronous
file operation.

Recommendation: keep `call_log_pipeline_enabled=0`. For production API keys where bodies are not
required for support, set the existing `noLog` policy: `chatCore` detects it before enabling detail
logging, and `saveCallLog()` nulls body/pipeline payloads while retaining the summary call row
([open-sse/handlers/chatCore.ts:756](../../open-sse/handlers/chatCore.ts#L756),
[src/lib/usage/callLogs.ts:552](../../src/lib/usage/callLogs.ts#L552)). That saves essentially the
entire artifact projection—0.394 GB/day and one sync write/rename per request at x10; 3.94 GB/day and
one sync write/rename per request at x100—while preserving bounded summary diagnostics.

## 4. Crash recovery and billing durability

SQLite WAL recovery itself is sound for committed transactions. The build sets WAL with
`synchronous=NORMAL` ([src/lib/db/core.ts:1119](../../src/lib/db/core.ts#L1119)). In an isolated
`node:sqlite` WAL/NORMAL SIGKILL test, a committed row survived, an open uncommitted transaction did
not, both reopened databases returned `quick_check=ok`, and journal mode remained WAL
([E6](#e6-isolated-unclean-kill-test)). Therefore an ordinary container kill does not imply a
corrupted database or loss of rows whose commit returned. `NORMAL`, however, offers weaker
power-loss durability than `FULL`; a host/kernel/storage failure is a different threat from a process
kill.

Graceful SIGTERM/SIGINT is correctly wired to drain requests, flush the cost buffer, checkpoint and
close SQLite ([src/lib/gracefulShutdown.ts:95](../../src/lib/gracefulShutdown.ts#L95),
[src/lib/gracefulShutdown.ts:129](../../src/lib/gracefulShutdown.ts#L129),
[src/lib/db/core.ts:1236](../../src/lib/db/core.ts#L1236)). SIGKILL, OOM kill, or a watchdog that
does not allow that handler to finish bypasses those protections.

The revenue risks are **an unobservable failed commit and an in-memory cost buffer**, not proven loss
of an already committed usage row:

- Both usage paths invoke `saveRequestUsage()` without awaiting or inspecting it
  ([open-sse/handlers/chatCore/nonStreamingUsageStats.ts:42](../../open-sse/handlers/chatCore/nonStreamingUsageStats.ts#L42),
  [open-sse/handlers/chatCore/streamingUsageStats.ts:33](../../open-sse/handlers/chatCore/streamingUsageStats.ts#L33)).
  The callee catches DB errors, logs, and resolves without retry or a durable queue
  ([src/lib/usage/usageHistory.ts:703](../../src/lib/usage/usageHistory.ts#L703)). A busy/I/O/constraint
  failure can therefore omit a billing row while the response path cannot detect it. WAL cannot
  recover work that never committed.
- Cost rows remain in memory for as long as 60 seconds or 1,000 entries. Failed flushes are requeued
  only in memory, and only graceful shutdown forces a flush
  ([src/lib/spend/batchWriter.ts:63](../../src/lib/spend/batchWriter.ts#L63),
  [src/lib/spend/batchWriter.ts:115](../../src/lib/spend/batchWriter.ts#L115),
  [src/lib/gracefulShutdown.ts:99](../../src/lib/gracefulShutdown.ts#L99)). An unclean kill loses that
  buffer.

Because one lost billable usage event is lost revenue, make the billing event durable before
signaling completion. The current `async` function contains no `await` before its synchronous
transaction, so a normal invocation ordinarily commits before its already-resolved Promise callback
runs; nevertheless, the caller neither verifies success nor receives a failure because the callee
catches it ([src/lib/usage/usageHistory.ts:607](../../src/lib/usage/usageHistory.ts#L607),
[src/lib/usage/usageHistory.ts:703](../../src/lib/usage/usageHistory.ts#L703)). Change the contract to
return a persisted/not-persisted result and require the request completion path to check it, or append
to a local durable outbox that an asynchronous consumer drains idempotently. Add an idempotency key
and alert on persistence failures/backlog. Set `synchronous=FULL` for revenue-bearing storage after a
controlled copied-DB and production-latency validation; the copy benchmark showed no meaningful
throughput cost, but that is not authorization to change production. This durability work has higher
priority than a database backend migration.

Artifacts and call rows are also not one atomic unit: the file is renamed before the DB insert
([src/lib/usage/callLogs.ts:624](../../src/lib/usage/callLogs.ts#L624)). A kill in between can leave an
orphan file, which the rotation pass later removes. This is a diagnostics consistency issue, not a
billing guarantee.

## 5. Issue #5618 and bounded-query audit

The #5618 startup OOM fix is present. The helper explicitly pages artifact references in 5,000-row
chunks and selects deletion IDs in bounded pages
([src/lib/usage/callLogsBoundedQueries.ts:3](../../src/lib/usage/callLogsBoundedQueries.ts#L3)).
`cleanupOrphanCallLogFiles()` and `deleteCallLogsBefore()` use it
([src/lib/usage/callLogs.ts:340](../../src/lib/usage/callLogs.ts#L340),
[src/lib/usage/callLogs.ts:429](../../src/lib/usage/callLogs.ts#L429)); ordinary call-log listing
defaults to 200 rows ([src/lib/usage/callLogs.ts:816](../../src/lib/usage/callLogs.ts#L816)). The
deployed container also contains `/app/src/lib/usage/callLogsBoundedQueries.ts` ([E4](#e4-running-process-and-log-observations)).
The startup path that failed around a 170 MB DB is covered.

The fix does **not** cover every cardinality-unbounded query. User-triggered `exportCallLogsSince()`
materializes every matching ID and then every log object
([src/lib/usage/callLogs.ts:915](../../src/lib/usage/callLogs.ts#L915)). JSON backup exports execute
unbounded `.all()` over `usage_history` and `domain_cost_history`
([src/lib/db/usageAnalytics.ts:743](../../src/lib/db/usageAnalytics.ts#L743)). These are not startup
queries, but at x100 with long retention they remain OOM risks. Stream/page exports or impose an
explicit maximum before increasing row retention.

## 6. PostgreSQL or external database path

OmniRoute has no PostgreSQL, MySQL, or external relational backend. `SqliteAdapter.driver` accepts
only `better-sqlite3`, `node:sqlite`, and `sql.js`, and exposes synchronous `prepare().run/get/all`,
PRAGMA, and synchronous transaction semantics
([src/lib/db/adapters/types.ts:12](../../src/lib/db/adapters/types.ts#L12)). The factory tries those
three SQLite implementations in order
([src/lib/db/adapters/driverFactory.ts:37](../../src/lib/db/adapters/driverFactory.ts#L37),
[src/lib/db/adapters/driverFactory.ts:120](../../src/lib/db/adapters/driverFactory.ts#L120)); the
database path is always `DATA_DIR/storage.sqlite`
([src/lib/db/core.ts:84](../../src/lib/db/core.ts#L84)). No backend-selection environment variable or
migration tool for another database was found.

This is deep coupling, not a connection-string swap. Repository counts on this commit found 116
files calling `getDbInstance`, 965 `.prepare(` calls across 123 files, 626 SQLite-specific SQL/API
pattern hits across 165 files, and 119 SQL migrations ([E7](#e7-sqlite-coupling-counts)). A serious
PostgreSQL migration requires asynchronous repository interfaces, query and DDL/upsert/date rewrites,
transaction-semantics changes, migration translation, dual-write/backfill/cutover tooling, and broad
integration testing. It is a large project.

That project is not justified by the corrected x100 traffic. If retention requirements later demand
tens of millions of queryable telemetry rows, split the data by purpose: keep SQLite for provider,
routing, credential, and bounded operational state; send append-only request/usage telemetry through
a durable queue to object storage and an analytical store. PostgreSQL becomes appropriate if the
control-plane itself requires remote concurrent writers, but that topology decision is outside this
report.

## 7. Phased recommendation

### Do first: nearly free

1. **Keep `call_log_pipeline_enabled=0`, remove the stale camel-case ambiguity, and enable `noLog` for
   client keys that do not require body diagnostics.** At x10 this avoids about 0.394 GB artifact
   writes/day; at x100 about 3.94 GB/day, plus one synchronous write/rename per request. If bodies are
   required, retain a short sampled/error-only policy rather than all successful bodies.
2. **Set every retention value explicitly and alert on it.** At minimum set call age/row/artifact,
   proxy row/age, usage raw retention, cost-history retention, app-log size/age/count, and managed
   backup age. Defaults and dashboard values currently disagree, and several policies run only at
   startup. The values are business choices; do not infer 365 days of raw billing rows merely because
   the dashboard currently says 365.
3. **Wire one production cleanup scheduler, remove the duplicate proxy cleanup call in its current
   implementation, and avoid synchronous `VACUUM` on the request process.** Run bounded deletes and
   rollups on a controlled schedule. At x100 this prevents roughly 1.093 GB/day of four-table/index
   growth from accumulating beyond policy; the exact reclaimed physical bytes depend on page reuse
   and checkpoint/VACUUM policy.
4. **Fix and test application-log reopen/rotation.** At the extrapolated x10/x100 rates, a correct
   seven-day cap bounds about 0.81/8.1 GB; rotation does not lower the projected 116 MB/1.16 GB daily
   write I/O. Reduce duplicated Pino/console logging if that I/O matters.
5. **Owner-review then archive/delete the unreferenced top-level backups.** This reclaims 0.969 GB
   now (0.536 GB from April-June) and saves no recurring I/O. Set nonzero managed backup age and verify
   restores; retention is not a substitute for backups.

### x10: cheap changes on this box

Keep SQLite. Implement the billing outbox/awaited write and `FULL` durability validation; make cleanup
and app rotation observable; cap/stream exports; select a body-artifact sampling policy; monitor DB,
WAL, artifact, log, cleanup duration, usage-write failures, and outbox backlog. The measured SQLite
capacity margin is over 1,800 times the 2.1 request/second peak, so tuning and correctness dominate.

### x100: architecture, but not PostgreSQL by default

Keep the same SQLite control-plane because 20.8 requests/second is far below its measured ceiling.
Make billing ingestion durably idempotent before acknowledging completion. Retain only bounded
operational summaries locally. If the business requires long-lived full request bodies or raw
request-level analytics, replace local JSON artifacts/unbounded history with a durable append queue,
object storage for payloads, and a columnar analytics store; keep searchable references and short
hot retention locally. Reconsider PostgreSQL only when a separately established concurrent-writer or
control-plane availability requirement demands it.
